# 本地轻量大模型 OCR 纠错与合同智能分析 · 可行性分析

- 版本：v1.0
- 日期：2026-11-20
- 适用产品：红笔 Red Pen（Android / Windows / Web）
- 结论摘要：**技术上可行，建议采用“规则优先、模型增强、桌面先行、移动分级”的分阶段方案**。不建议让大模型直接替代现有规则判定，也不建议在移动端默认内置 7B 级模型。

---

## 1. 背景与目标

红笔当前的处理链路是：

```text
图片 / PDF / DOCX / TXT
        │
        ├─ Android：ML Kit 中文离线 OCR
        ├─ Windows：系统 OCR / 内嵌文本提取
        └─ 文本层：解析、清洗、分段
                │
                ▼
        engine.dart / engine.js 规则引擎（R1–R20）
                │
                ▼
        红线 / 黄线 / 灰线 / 绿线 + 依据 + 问法 + 改法
```

要解决的问题是：OCR 结果中的错字、漏字、串行、数字/日期误识别，会直接影响规则命中与金额计算；同时，规则引擎对同义表述、口语化条款、跨句语义的覆盖仍有边界。

目标方案：

```text
OCR 原始文本
   │
   ▼
轻量本地模型纠错（只改错，不改意思）
   │
   ▼
结构化合同文本（条款分段 + 关键字段）
   │
   ├─ 规则引擎：确定性判定、金额计算、法条映射
   └─ 本地模型：语义补充、解释生成、缺失条款提示
                │
                ▼
        带证据引用的风险报告
```

本报告评估五个问题：

1. 本地模型怎么选，性能和合同场景是否匹配；
2. OCR 纠错准确率能提升多少，边界在哪里；
3. 合同分析能覆盖哪些能力，哪些必须继续用规则；
4. Windows / Android 的硬件资源要求；
5. 落地成本、风险与分阶段建议。

---

## 2. 现状约束与设计原则

### 2.1 现状约束

| 约束 | 说明 |
|---|---|
| 隐私 | 合同正文只在用户设备本地处理，不上传服务器 |
| 离线 | 核心功能断网可用；网络仅用于检查 GitHub 发行版 |
| 确定性 | 同一份合同应得到可复核、可回归的结论 |
| 体积 | 当前 Windows 安装包约 18.6 MB，Android APK 约 39–49 MB |
| 双端一致 | Web / Android / Windows 共用同一套规则语义 |
| 可解释 | 每条结论必须能回到原文、法条和具体金额 |

### 2.2 设计原则

1. **规则是裁判，模型是助手**。模型可以纠错、抽取、解释、提示遗漏，但不能直接推翻规则判定。
2. **先纠错，再分析**。纠错结果必须保留原文对照，允许用户一键还原。
3. **只改“形”，不改“义”**。数字、日期、金额、比例、法条序号默认不交给模型自由改写。
4. **证据引用优先**。模型输出的每条结论必须带原文片段和位置，不能凭空生成法条。
5. **桌面先行，移动分级**。Windows 承载 3B–7B，Android 承载 0.5B–1.5B 或纯规则。
6. **模型可替换**。推理层与模型解耦，允许 GGUF / ONNX / 系统 API 多种后端。

## 3. 方案总览

### 3.1 推荐架构

```text
┌──────────────────────────────────────────────────────────┐
│ 输入层：图片 / 扫描 PDF / DOCX / 文本                     │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│ OCR 层                                                    │
│  Windows：PaddleOCR / 系统 OCR / 内嵌文本                  │
│  Android：ML Kit 中文离线模型                              │
│  输出：带坐标、置信度、行块的原始文本                       │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│ 纠错层（本地轻量模型 + 确定性守卫）                         │
│  1. 版面还原：去页眉页脚、合并断行、修复串列                │
│  2. 混淆集替换：形近字、同音字、全半角、标点                │
│  3. 轻量模型：整句纠错 / 术语校正 / 断句                   │
│  4. 守卫：数字、日期、金额、比例、法条序号不自动改          │
│  5. 差异输出：原文 / 纠错文 / 变更点                        │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│ 结构化层                                                  │
│  条款分段、编号识别、当事人/期限/工资/社保/竞业等字段抽取   │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│ 分析层                                                    │
│  规则引擎 R1–R30：判定、金额、法条、分级                    │
│  本地模型：同义改写识别、跨句语义、缺失条款提示、解释生成   │
│  融合策略：规则结论优先，模型只补充“未命中”和“解释”        │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│ 输出层：风险卡片 + 原文引用 + 依据 + 问法 + 改法 + 置信度   │
└──────────────────────────────────────────────────────────┘
```

### 3.2 为什么不是“端到端大模型读合同”

| 做法 | 问题 |
|---|---|
| 直接把合同丢给 7B 模型出结论 | 法条可能编造；同一合同多次输出不一致；无法回归测试 |
| 模型直接算金额和期限 | 数字/日期错误会被放大；责任无法界定 |
| 模型直接判“有效/无效” | 法律判断需要规则与个案事实，模型只能给倾向 |
| 纯模型方案 | 小模型能力不足，大模型体积/延迟不可接受 |

因此采用 **“OCR + 纠错 + 规则 + 模型增强”** 的混合架构，而不是端到端替代。

## 4. 本地模型选型与性能匹配

### 4.1 候选模型

| 模型 | 参数量 | Q4 量化后体积（约） | 中文能力 | 合同场景适配 | 建议用途 |
|---|---:|---:|---|---|---|
| Qwen2.5-0.5B-Instruct | 0.5B | 0.4–0.6 GB | 基础 | 只能做短句纠错/分类 | Android 低端机、兜底 |
| Qwen2.5-1.5B-Instruct | 1.5B | 1.0–1.3 GB | 较好 | 纠错、字段抽取、短解释 | Android 中高端、Windows 轻量 |
| Qwen2.5-3B-Instruct | 3B | 2.0–2.6 GB | 好 | 纠错、条款抽取、解释 | Windows 主力 |
| Qwen3-4B-Instruct | 4B | 2.6–3.2 GB | 好 | 推理与结构化输出 | Windows 备选 |
| Qwen2.5-7B-Instruct | 7B | 4.5–5.5 GB | 很好 | 复杂条款解释、长文分析 | Windows 高配可选 |
| GLM-4-9B-Chat | 9B | 5.5–7 GB | 很好 | 中文合同理解 | Windows 高配，体积偏大 |
| Llama-3.1-8B-Instruct | 8B | 5–6 GB | 中等 | 英文合同更好 | 暂不作为中文首选 |
| Yi-1.5-6B-Chat | 6B | 4–5 GB | 好 | 中文理解 | 备选 |

> 体积为 GGUF Q4_K_M 量级估算，实际以具体量化版本为准。模型许可证需在发布前逐一复核，优先选择 Apache 2.0 或明确允许商用的模型。

### 4.2 OCR 引擎选型

| 引擎 | 平台 | 中文印刷体 | 手写体 | 体积 | 说明 |
|---|---|---|---|---|---|
| ML Kit 中文离线 | Android | 好 | 弱 | 随 APK，约几十 MB | 当前已接入，保留 |
| PaddleOCR PP-OCRv5 mobile | Windows / Android | 很好 | 中等 | 检测+识别约 20–50 MB | 中文合同首选，需 ONNX/NCNN 运行时 |
| RapidOCR（ONNX） | Windows / Android | 好 | 弱 | 约 15–30 MB | 部署简单，适合 Windows 初版 |
| Windows OCR API | Windows | 中等 | 弱 | 系统自带 | 零体积，作为兜底 |
| Tesseract 5 | 跨平台 | 中等 | 弱 | 约 30–80 MB | 中文效果一般，不推荐主力 |

**建议**：Windows 优先 PaddleOCR mobile，Android 保留 ML Kit；两者输出统一为“行块 + 坐标 + 置信度”的内部结构，纠错层不依赖具体 OCR 引擎。

### 4.3 推理运行时

| 运行时 | 平台 | 优点 | 缺点 |
|---|---|---|---|
| llama.cpp（GGUF） | Windows / Android | 部署简单、CPU 友好、量化成熟 | Android 需自行编译/JNI |
| Ollama | Windows | 开发调试快 | 不适合随应用分发 |
| ONNX Runtime GenAI | Windows / Android | 与 OCR 统一运行时、可做图优化 | 模型转换链路较长 |
| MLC-LLM | Android | 移动端 GPU 加速 | 生态与模型覆盖有限 |
| 系统 AI API | Windows / Android | 零体积、低功耗 | 可用性/版本碎片化，不可控 |

**建议**：Windows 用 llama.cpp + GGUF Q4_K_M；Android 用 llama.cpp JNI 或 ONNX Runtime，先做 1.5B 以内的模型。

### 4.4 性能匹配（量级估算）

以下为“合同 3,000–8,000 字、纠错 + 字段抽取”的端到端时间估算，实际以目标机型实测为准。

| 设备档位 | 典型硬件 | 模型 | 纠错延迟 | 字段抽取 | 综合体验 |
|---|---|---|---:|---:|---|
| Windows 高配 | i7/Ryzen 7 + 32GB + RTX 4060 8GB | 7B Q4 | 5–12 s | 3–8 s | 可接受，适合深度分析 |
| Windows 主流 | i5/Ryzen 5 + 16GB 核显 | 3B Q4 | 4–10 s | 2–6 s | 推荐档位 |
| Windows 轻量 | 8GB 内存旧机 | 1.5B Q4 | 3–8 s | 1–4 s | 可用，建议只做纠错 |
| Android 高端 | 骁龙 8 Gen 2 / 12GB | 1.5B Q4 | 8–20 s | 5–15 s | 可用，注意发热 |
| Android 中端 | 骁龙 7 系 / 8GB | 1.5B Q4 | 15–40 s | 10–30 s | 体验偏慢，建议可选 |
| Android 低端 | 6GB 以下 | 0.5B 或纯规则 | 10–30 s | — | 不建议默认开启 |

关键结论：

- **Windows 3B 是甜点档**：体积约 2–3 GB，16GB 内存可跑，延迟可接受。
- **7B 适合“可选增强包”**，不适合默认内置。
- **Android 1.5B 是上限**；再大则体积、内存、发热和耗电都难以接受。
- 纠错比分析更轻：如果只做 OCR 纠错，模型可以更小、上下文更短、延迟更低。

## 5. OCR 纠错准确率预期

### 5.1 OCR 错误类型

| 类型 | 例子 | 对合同分析的影响 | 纠错难度 |
|---|---|---|---|
| 形近字 | 己/已/巳、未/末、土/士 | 条款语义变化 | 中 |
| 同音字 | 权利/权力、定金/订金 | 法律概念变化 | 中 |
| 数字误识别 | 3,000 → 30,00、8% → 80% | 金额/比例错误 | 高，必须守卫 |
| 日期误识别 | 2026 → 2028 | 期限判断错误 | 高，必须守卫 |
| 断行/串列 | 两栏文本交错 | 条款错位 | 高 |
| 漏字/多字 | “不”字漏识别 | 语义反转 | 高 |
| 标点/全半角 | 全角逗号、句号缺失 | 分段错误 | 低 |
| 页眉页脚 | 页码混入正文 | 干扰规则 | 低 |

### 5.2 预期收益

以印刷体合同扫描件为基线（OCR 字符错误率 CER 约 1%–5%）：

| 指标 | 引入纠错前 | 引入轻量模型后（预期） | 说明 |
|---|---:|---:|---|
| 印刷体 CER | 1%–5% | 0.7%–3.5% | 相对下降约 20%–40% |
| 拍照/倾斜件 CER | 3%–10% | 2%–7% | 受版面还原影响更大 |
| 关键字段准确率 | 80%–90% | 88%–95% | 当事人、期限、工资、试用期 |
| 数字/日期准确率 | 90%–97% | 95%–99% | 必须配合正则/校验，不应只靠模型 |
| 规则命中召回 | 80%–90% | 85%–94% | 纠错减少“关键字被错字破坏” |
| 过度纠错率 | — | 控制在 <1% | 数字/日期/法条序号零容忍 |

> 这些是规划用估算，不是承诺值。必须用真实合同样本建立评测集，按“纠错前后规则结论差异”评估，而不是只看 CER。

### 5.3 纠错策略

**建议采用“三层纠错”，模型只负责第三层：**

1. **确定性层（必须）**
   - 全半角统一、空白/换行规范、页眉页脚剔除；
   - 常见 OCR 混淆集替换（己/已、未/末、土/士等）；
   - 法律术语词典：劳动合同、试用期、竞业限制、经济补偿等；
   - 数字/日期/金额/比例正则校验，发现异常只提示不改写。

2. **轻量模型层（增强）**
   - 输入：单句或相邻 2–3 句，避免长上下文漂移；
   - 任务：只纠正明显 OCR 错误，不改变语义；
   - 输出：JSON `{corrected, changes:[{from,to,reason,confidence}]}`；
   - 参数：temperature 0、top_p 1、最大输出限制；
   - 守卫：数字、日期、百分比、法条序号、专有名词默认锁定。

3. **人工确认层（兜底）**
   - 展示原文/纠错文差异；
   - 高影响变更（金额、期限、是否、不得）必须用户确认；
   - 一键还原原文。

### 5.4 评测方法

建立 100–300 份真实合同的评测集，标注：

- OCR 原文、人工校对文本；
- 关键字段真值（当事人、期限、试用期、工资、社保、竞业、违约金）；
- 规则应命中项（R1–R30）。

指标：

- CER / WER；
- 关键字段 exact match / F1；
- 规则命中 recall / precision；
- 过度纠错率（把正确内容改错的样本比例）；
- 数字/日期错误零容忍通过率；
- 端到端延迟与内存峰值。

## 6. 合同分析核心能力覆盖

### 6.1 能力矩阵

| 能力 | 规则引擎 | 本地模型 | 建议分工 |
|---|---|---|---|
| 条款分段与编号 | 强 | 中 | 规则为主，模型修复断行/串列 |
| 关键字段抽取 | 强（模板） | 强（语义） | 规则兜底，模型补漏 |
| 试用期/工资/社保计算 | 强 | 弱 | 只用规则，模型不参与计算 |
| 违约金/竞业/服务期 | 强 | 中 | 规则判定，模型解释 |
| 同义/口语句式识别 | 中 | 强 | 模型召回，规则复核 |
| 跨句/跨条款引用 | 弱 | 中 | 模型提示，规则确认 |
| 缺失条款提示 | 中 | 强 | 模型提示，规则清单核对 |
| 法条引用 | 强（内置） | 弱（易编造） | 只用规则/RAG，不让模型自由生成 |
| 风险分级 | 强 | 中 | 规则定级，模型只补充理由 |
| 谈判话术/替换条款 | 强（模板） | 强（生成） | 模板为主，模型润色 |
| 地方标准/最低工资 | 弱 | 弱 | 需要外部数据源，模型不可靠 |
| 手写体/表格 | 弱 | 中 | OCR 能力决定上限 |

### 6.2 建议的融合策略

```text
规则命中 ──► 直接输出判定（模型只负责解释/润色）
规则未命中 ──► 模型语义扫描 ──► 生成“疑似风险”候选
                              ──► 规则二次复核 ──► 确认后输出
规则与模型冲突 ──► 规则优先，模型结论降级为“提示”
```

**原则**：

- 规则输出是“结论”，模型输出是“候选/解释”。
- 模型不得生成法条序号；法条只能来自内置法条库/RAG 检索结果。
- 模型输出必须带原文引用；无引用的结论不展示。
- 所有模型输出进入“灰线/待确认”，除非规则复核确认。

### 6.3 可覆盖的新规则（R21–R30）

`docs/rules-v2.json` 已定义 10 条新规则，本地模型可以显著提升其召回：

| 规则 | 模型可增强点 |
|---|---|
| R21 必备条款缺失 | 识别“其他按公司规定”等模糊表述，提示缺失项 |
| R22 经济补偿 | 识别“买断工龄/一次性安置”等同义表述 |
| R23 无固定期限 | 识别“一年一签/第三次签”等口语描述 |
| R24 特殊工时 | 识别“按季度算加班/轮班制”等非标准表述 |
| R25 三期保护 | 识别“计划内生育/排队怀孕”等隐晦限制 |
| R26 工伤 | 识别“意外与公司无关/商业险赔完就算”等变体 |
| R27 个人信息 | 识别“入职审核/资历核实”等背调变体 |
| R28 非全日制/派遣/外包 | 识别“假外包/真派遣”的实际管理描述 |
| R29 电子签署 | 识别“平台点确认/不给下载”等文本交付问题 |
| R30 争议管辖 | 识别“只能去公司所在地仲裁”等排除性表述 |

### 6.4 能力边界

以下场景不建议依赖本地小模型：

- 需要实时地方最低工资、社保基数、公积金比例；
- 需要判断复杂的劳动关系认定（事实优先，需证据）；
- 需要计算经济补偿、加班费、年假折算的精确金额；
- 需要判断条款是否“显失公平”；
- 手写体、严重倾斜、低分辨率扫描件；
- 多栏排版、表格跨页、印章遮挡。

这些场景应由规则、数据源和人工复核共同处理。

## 7. 本地运行硬件资源要求

### 7.1 Windows

| 档位 | CPU | 内存 | GPU | 磁盘 | 可运行模型 | 体验 |
|---|---|---|---|---|---|---|
| 最低 | 4 核 | 8 GB | 无 | 3 GB 空闲 | 1.5B Q4 | 只建议纠错 |
| 推荐 | 6–8 核 | 16 GB | 无/核显 | 6 GB 空闲 | 3B Q4 | 纠错 + 字段抽取 |
| 高配 | 8 核+ | 32 GB | RTX 3060 12GB+ | 10 GB 空闲 | 7B Q4 | 深度分析 |
| 极限 | 12 核+ | 64 GB | RTX 4090 24GB | 20 GB 空闲 | 14B Q5 | 研究/批量 |

说明：

- 3B Q4 在 16GB 内存机器上，模型加载后常驻内存约 2.5–3.5GB，需给系统和应用留足余量。
- 7B Q4 建议 16GB 起步，32GB 更稳；GPU 显存 8GB 可放下 7B Q4，但上下文长度受限。
- 模型文件建议按需下载，不默认塞进安装包。

### 7.2 Android

| 档位 | 内存 | 芯片 | 可运行模型 | 建议 |
|---|---|---|---|---|
| 低端 | 6 GB 以下 | 入门 4G/5G | 0.5B Q4 或纯规则 | 默认关闭模型 |
| 中端 | 8 GB | 骁龙 7 系/天玑 8000 | 1.5B Q4 | 可选开启纠错 |
| 高端 | 12 GB+ | 骁龙 8 系/天玑 9000 | 1.5B Q4 | 可默认开启纠错 |

移动端限制：

- 模型常驻内存会触发系统杀后台；
- 长时间推理导致发热、降频、耗电；
- NNAPI/GPU delegate 对 LLM 支持不稳定；
- APK 体积每增加 1GB，安装与更新成本显著上升；
- 应用商店/分发渠道对包体大小敏感。

**建议**：Android 默认只做规则 + 确定性纠错；1.5B 模型作为“可选增强包”下载，用户手动开启。

| 工作项 | 内容 | 量级 |
|---|---|---|

| 纠错层 | 混淆集、词典、数字守卫、差异 UI | 3–5 人周 |

### 8.2 持续成本

| 项目 | 说明 |
|---|---|
| 模型更新 | 每季度评估新模型，需回归测试 |

### 8.3 成本优化建议

1. **模型按需下载**：安装包保持轻量，模型作为可选组件。
2. **桌面优先**：Windows 用户对体积/性能容忍度更高，先验证价值。
3. **移动端只做小模型**：1.5B 以内，或纯规则 + 确定性纠错。
4. **复用现有 OCR**：Android 保留 ML Kit，Windows 先接系统 OCR/PaddleOCR，避免重复投入。
5. **规则库继续扩展**：规则的成本远低于模型，且可回归、可解释。

## 9. 技术风险与应对

| 风险 | 影响 | 概率 | 应对 |
|---|---|---|---|
| 模型编造法条 | 报告不可信，法律风险 | 中 | 法条只来自内置库/RAG；模型不得生成条号；引用必须可点击核对 |
| 过度纠错 | 把正确内容改错 | 中高 | 数字/日期/金额/比例锁定；差异展示；一键还原；<1% 过度纠错门槛 |
| OCR 错误放大 | 规则误判 | 高 | 多引擎交叉校验；低置信度行标黄；关键字段要求用户确认 |
| 移动端性能/发热 | 体验差、被系统杀 | 高 | 1.5B 上限；可选开启；超时降级到规则；后台任务限制 |
| 模型体积 | 安装/更新成本高 | 高 | 按需下载；模型与安装包分离；差分更新 |
| 许可证风险 | 无法商用 | 中 | 发布前复核模型许可证；优先 Apache 2.0 |
| 隐私泄露 | 合同内容外泄 | 低（本地） | 全程本地；禁用遥测；不调用外部 API；日志脱敏 |
| 结果不确定 | 同一合同结论漂移 | 中 | temperature 0；固定 prompt；模型版本锁定；规则兜底 |
| 版本碎片 | 不同设备结果不同 | 中 | 模型/运行时版本写入报告；最低版本要求 |
| 法律免责 | 用户误以为正式法律意见 | 中 | 明确“辅助审阅，不构成法律意见”；建议人工复核 |

### 9.1 关键守卫规则

```text
数字守卫：金额、日期、百分比、期限、法条序号默认不自动修改
引用守卫：模型结论必须带原文片段；无引用不展示
规则守卫：规则命中优先；模型冲突时降级为提示
置信守卫：低置信度输出进入“待确认”，不进入红线
版本守卫：报告记录 OCR/模型/规则版本，便于复现
```

## 10. 分阶段落地建议

### 阶段 0：确定性增强（现在即可做，1–2 周）

- 统一 OCR 输出结构：行块、坐标、置信度；
- 增加法律术语词典与 OCR 混淆集；
- 数字/日期/金额/比例正则校验；
- 纠错差异展示与一键还原；
- 建立 30–50 份合同的初版评测集。

**目标**：不引入模型，先把“可确定修复”的错误处理掉，验证评测流程。

### 阶段 1：桌面轻量模型 PoC（1–2 个月）

- Windows 接入 llama.cpp + Qwen2.5-1.5B/3B Q4；
- 只做 OCR 纠错与条款分段，不做最终判定；
- 与现有规则引擎并联，A/B 对比；
- 评测 CER、字段准确率、规则命中变化、延迟/内存。

**Go 条件**：

- CER 相对下降 ≥20%；
- 数字/日期过度纠错率 <1%；
- 关键字段 F1 ≥0.85；
- 3B 模型在 16GB 机器上端到端 ≤15 秒；
- 规则结论无回归。

### 阶段 2：合同分析增强（2–4 个月）

- 增加字段抽取 schema 与条款分类；
- 模型输出“疑似风险候选”，规则二次复核；
- 引入法条 RAG（内置法条库 + 检索），禁止模型自由生成条号；
- 报告增加置信度、原文引用、纠错记录；
- 接入 R21–R30 规则，模型负责同义/口语召回。

**目标**：模型提升召回，规则保证确定性；所有新增结论可回溯。

### 阶段 3：移动端分级（3–6 个月）

- Android 接入 1.5B 以内的量化模型，作为可选增强包；
- 低端机默认纯规则 + 确定性纠错；
- 模型下载、开关、超时降级、内存监控；
- 评估发热、耗电、杀后台与包体增长。

**不建议**：在 Android 默认内置 3B 以上模型，或把模型作为唯一分析路径。

## 11. 结论

### 11.1 可行性评级

| 维度 | 评级 | 说明 |
|---|---|---|
| 技术可行性 | **可行** | OCR、轻量模型、规则引擎均有成熟方案 |
| 桌面端体验 | **推荐** | 3B Q4 在主流 Windows 机器可接受 |
| 移动端体验 | **有条件可行** | 1.5B 以内可选，默认模型不推荐 |
| 准确率提升 | **中等** | 印刷体纠错收益明确，手写/复杂版面有限 |
| 合同分析覆盖 | **规则为主、模型增强** | 不能替代规则与人工复核 |
| 成本 | **可控** | 无 API 费用，主要是工程与模型分发成本 |
| 风险 | **可管理** | 关键在数字守卫、引用守卫、规则优先 |

### 11.2 最终建议

1. **采用混合架构，不做端到端替代**：规则引擎继续负责判定、金额、法条；模型负责纠错、抽取、解释、同义召回。
2. **Windows 先行**：以 Qwen2.5-3B-Instruct Q4 为主力，16GB 内存、无独显也可运行；7B 作为高配可选。
3. **Android 分级**：默认纯规则 + 确定性纠错；1.5B 模型作为可选下载包，低端机不默认开启。
4. **先做纠错，再做分析**：纠错的价值更容易量化，风险更低；分析增强必须建立在纠错和结构化稳定之后。
5. **建立评测闭环**：没有评测集就不要上线模型；每次模型/提示词/规则变更都要回归。
6. **守住三条底线**：数字/日期不自动改；法条不由模型生成；规则结论优先于模型结论。

### 11.3 建议的下一步

| 优先级 | 动作 | 产出 |
|---|---|---|
| P0 | 建立 50 份合同评测集与纠错基线 | CER、字段准确率、规则命中率 |
| P0 | 实现确定性纠错层（词典/混淆集/数字守卫） | 可上线的纠错模块 |
| P1 | Windows 接入 1.5B/3B Q4，做 A/B | PoC 报告与 Go/No-Go 决策 |
| P1 | 规则 R21–R30 运行时接入 | 规则覆盖率提升 |
| P2 | 法条 RAG 与引用守卫 | 可核对的解释生成 |
| P2 | Android 1.5B 可选包 | 移动端增强体验 |
| P3 | 7B 高配增强包 | 深度分析模式 |
