# 1B–1.5B 轻量模型专项训练与知识蒸馏 · 可行性分析

- 版本：v1.0
- 日期：2026-11-20
- 适用产品：红笔 Red Pen（Android / Windows）
- 研究对象：1B–1.5B 参数规模的本地轻量模型
- 业务目标：OCR 纠错 + 合同条款辨认/结构化
- 结论摘要：**可行，但应定位为“识别与纠错助手”，不是“法律判断引擎”**。推荐以 Qwen2.5-1.5B-Instruct 为基座，采用“LoRA/QLoRA 微调 + 7B/14B 教师模型蒸馏 + 规则约束解码”的路线；桌面端优先，移动端作为可选增强包。

---

## 1. 问题定义

### 1.1 两个任务不要混在一起

| 任务 | 输入 | 输出 | 成功标准 | 是否适合 1.5B |
|---|---|---|---|---|
| OCR 纠错 | OCR 原始文本/行块 | 纠正后的文本 + 变更点 | CER 下降、数字/日期不被改错 | 适合，任务窄、上下文短 |
| 合同条款辨认 | 纠错后的合同文本 | 条款类型、关键字段、对应规则 ID、证据片段 | 条款召回率、字段 F1、规则映射准确率 | 适合做“辨认/抽取”，不适合做最终法律判断 |

合同分析可以拆成四个子任务：

1. **条款分段**：把合同切成“试用期、工资、工时、社保、竞业、解除”等条款；
2. **条款分类**：判断一段文本属于哪类条款，映射到 R1–R30；
3. **字段抽取**：期限、试用期月数、工资、社保基数、竞业期限、违约金金额等；
4. **风险解释**：把规则引擎的结论转成用户能懂的话（可由模板完成，模型只做润色）。

1.5B 模型最适合 1–3；第 4 步应继续用规则模板，避免模型编造法条。

### 1.2 与现有规则引擎的关系

```text
OCR → 纠错模型 → 条款辨认模型 → 规则引擎（R1–R30）→ 结论
                     │                    │
                     └─ 候选条款/字段      └─ 确定性判定、金额、法条
```

- 模型负责“这段像什么条款”“关键数字在哪里”；
- 规则负责“是否违法/不利”“金额怎么算”“依据哪一条”；
- 模型输出必须带原文片段，规则复核后才进入报告。

## 2. 基座模型选型

### 2.1 候选基座

| 模型 | 参数量 | 中文能力 | 许可证 | 1.5B 档适配 | 建议 |
|---|---:|---|---|---|---|
| Qwen2.5-1.5B-Instruct | 1.5B | 强 | Apache 2.0 | 最佳 | **首选基座** |
| Qwen3-1.7B | 1.7B | 强 | Apache 2.0 | 很好 | 备选，需验证推理稳定性 |
| Qwen2.5-0.5B-Instruct | 0.5B | 中 | Apache 2.0 | 轻量 | 移动端兜底/分类 |
| MiniCPM-2B | 2B | 好 | 需核对 | 偏大 | 备选 |
| InternLM2.5-1.8B | 1.8B | 好 | Apache 2.0 | 偏大 | 备选 |
| Gemma-3-1B | 1B | 中 | Gemma 许可 | 轻量 | 中文合同场景需验证 |
| Llama-3.2-1B | 1B | 中 | Llama 许可 | 轻量 | 中文能力偏弱，不优先 |

**建议**：Qwen2.5-1.5B-Instruct 作为唯一主基座，避免多基座带来的评测和分发复杂度。Qwen3-1.7B 作为下一轮替换候选。

### 2.2 为什么不是更小的 0.5B

- 0.5B 可以做“条款分类/短句纠错”，但对长条款、否定句、数字上下文和 JSON 结构化输出容易崩；
- 1.5B 是“能稳定输出结构化结果”的下限；
- 移动端如果跑不动 1.5B，优先退回“规则 + 确定性纠错”，而不是强上 0.5B 模型。

## 3. 数据方案

### 3.1 OCR 纠错数据

| 数据来源 | 做法 | 规模建议 |
|---|---|---|
| 真实合同 + 人工校对 | 收集扫描件/照片，OCR 后人工校对，形成 paired data | 2,000–5,000 份 |
| 合成噪声 | 对干净合同做形近字、同音字、漏字、多字、断行、全半角扰动 | 50,000–200,000 句 |
| 公开 OCR 语料 | 中文印刷体/扫描件数据集，筛选合同相近版式 | 10,000–50,000 句 |
| 困难样本 | 数字、日期、金额、比例、否定词、法条序号 | 5,000–10,000 条 |

**关键**：不要只做“通用错字纠正”，要专门构造合同场景的困难样本：

- 数字：3,000 / 30,00 / 3000 / 3 000；
- 日期：2026 / 2028 / 2026年 / 2026.1；
- 比例：80% / 80‰ / 百分之八十 / 八成；
- 否定词：“不得”“无需”“不承担”被漏识别；
- 法律术语：竞业限制、服务期、经济补偿、无固定期限。

### 3.2 合同条款辨认数据

| 数据类型 | 标注内容 | 规模建议 |
|---|---|---|
| 条款分类 | 条款文本 → R1–R30 / 无风险 | 20,000–50,000 条 |
| 字段抽取 | 合同文本 → JSON（期限、试用期、工资、社保、竞业等） | 5,000–10,000 份 |
| 条款边界 | 条款起止位置、编号、标题 | 3,000–5,000 份 |
| 规则映射 | 条款 → 规则 ID + 证据片段 | 10,000–20,000 条 |
| 困难样本 | 同义/口语/否定/跨句引用 | 5,000–10,000 条 |

标注规范应直接复用 `docs/rules-v2.json`：

- 每条规则的正例/反例；
- 红/橙/绿判据；
- 必须引用的原文片段；
- 不允许模型生成的字段（法条序号、金额计算）。

### 3.3 数据质量原则

1. **一条样本只做一件事**：纠错样本不要混入风险判断；分类样本不要混入金额计算。
2. **保留原文位置**：每条输出必须能回到原文 span。
3. **负样本要真**：合法条款、已合规条款、单位承担费用的条款都要有，避免模型“见关键词就报警”。
4. **数字/日期单独评测**：不能只看整体 CER。
5. **去重与脱敏**：合同主体、身份证、电话、地址必须脱敏。

## 4. 训练方案

### 4.1 路线总览

```text
阶段 A：教师模型标注/生成
  7B/14B 教师 + 规则引擎 → 伪标签 → 人工抽检
        │
        ▼
阶段 B：1.5B 基座微调
  LoRA/QLoRA（先） → 全参数 SFT（后）
        │
        ▼
阶段 C：蒸馏与压缩
  序列级 KD +  rationale 蒸馏 + 量化（Q4/Q5）
        │
        ▼
阶段 D：约束解码与规则复核
  JSON Schema + 词典 + 数字守卫 + 规则引擎
```

### 4.2 OCR 纠错训练

**任务形式**：

```json
{
  "input": "试用期 6 个月，试用期工资为转正工资的 70%",
  "output": {
    "corrected": "试用期 6 个月，试用期工资为转正工资的 80%",
    "changes": [
      {"from": "70%", "to": "80%", "type": "number", "confidence": 0.62}
    ]
  }
}
```

> 注意：数字修改必须高置信度并进入人工确认；默认策略是“只标记、不自动改”。

**训练目标**：

- 主损失：corrected 文本的 token 交叉熵；
- 辅助损失：changes 的编辑分类（替换/删除/插入/保留）；
- 可选：copy 机制/指针网络，鼓励模型复制原文而非自由生成。

**推荐配置**：

| 项 | 建议 |
|---|---|
| 上下文 | 512–1024 tokens（单句/相邻 2–3 句） |
| LoRA rank | 16–32 |
| LoRA alpha | 32–64 |
| 学习率 | 1e-4 – 2e-4（LoRA）；1e-5 – 2e-5（全参） |
| batch | 32–64（梯度累积） |
| epoch | 2–4 |
| 精度 | bf16；QLoRA 4bit |
| 硬件 | 1×24GB 可做 LoRA；1×48GB 可做全参 |

### 4.3 条款辨认训练

**任务形式（统一 JSON）**：

```json
{
  "clauses": [
    {
      "type": "试用期期限",
      "ruleIds": ["R1"],
      "span": "其中试用期 6 个月",
      "fields": {"probationMonths": 6, "contractTermMonths": 24},
      "riskHint": "red"
    }
  ]
}
```

**训练目标**：

- 条款分类：多分类/多标签；
- 字段抽取：JSON 结构化输出；
- 规则映射：条款 → R1–R30；
- 证据片段：span 抽取（可用复制式解码）。

**推荐配置**：

| 项 | 建议 |
|---|---|
| 上下文 | 2048–4096 tokens（整份合同或分块） |
| 分块 | 按条款切分，保留标题与相邻上下文 |
| LoRA rank | 32–64 |
| 学习率 | 1e-4 – 2e-4 |
| epoch | 2–3 |
| 输出约束 | JSON Schema + 枚举（规则 ID 只能来自 R1–R30） |
| 硬件 | 1×24GB 可做 LoRA；1×48GB 可做全参 |

### 4.4 知识蒸馏

| 方法 | 做法 | 适用 |
|---|---|---|
| 序列级 KD | 教师生成完整答案，学生 SFT | 最简单，首选 |
| 分布级 KD | 教师 logits 蒸馏到学生 | 需要同 tokenizer/词表，成本高 |
| 推理链蒸馏 | 教师生成“为什么是这条规则”的解释，学生学 rationale | 提升可解释性 |
| 规则蒸馏 | 规则引擎生成确定性标签，学生学“条款→规则” | 成本最低、最可靠 |
| 拒绝采样 | 教师多采样，规则/人工筛选最佳答案 | 提升数据质量 |

**推荐组合**：

1. 规则引擎生成 30–50% 的高置信标签（条款→规则、字段→值）；
2. 7B/14B 教师生成同义/口语/跨句样本；
3. 人工抽检 5%–10%；
4. 1.5B 学生先 LoRA，再考虑全参；
5. 量化到 Q4_K_M，重新评测。

### 4.5 教师模型选择

| 教师 | 用途 | 备注 |
|---|---|---|
| Qwen2.5-7B-Instruct | 条款分类/字段抽取/解释 | 主力教师，成本可控 |
| Qwen2.5-14B-Instruct | 困难样本/长合同 | 质量更高，速度慢 |
| Qwen2.5-32B/72B | 小批量高质量标注 | 仅用于种子数据 |
| 规则引擎 | 确定性标签 | 不作为“教师模型”，但可作为标签源 |

> 不建议用闭源 API 生成全部训练数据：成本、合规、可复现性都不占优；可作为小批量对照。

## 5. 预期效果

### 5.1 OCR 纠错

| 指标 | 基座零样本 | LoRA 微调 | 蒸馏+量化 | 说明 |
|---|---:|---:|---:|---|
| 印刷体 CER | 2%–5% | 1.2%–3% | 1.3%–3.2% | 相对下降 30%–45% |
| 拍照/倾斜 CER | 4%–10% | 2.5%–6% | 2.8%–6.5% | 版面还原影响大 |
| 数字/日期 exact match | 90%–96% | 96%–99% | 95%–98.5% | 必须配合守卫 |
| 过度纠错率 | 2%–5% | 0.5%–1.5% | 0.6%–1.8% | 目标 <1% |
| 单句延迟（CPU） | 0.3–0.8s | 0.3–0.8s | 0.2–0.6s | 1.5B Q4 |

> 预期是“显著改善”，不是“消灭 OCR 错误”。数字、日期、比例必须继续用正则和人工确认兜底。

### 5.2 条款辨认

| 任务 | 基座零样本 | LoRA 微调 | 蒸馏+量化 | 说明 |
|---|---:|---:|---:|---|
| 条款分类准确率 | 65%–78% | 88%–94% | 86%–93% | 30 类 + 无风险 |
| 规则映射 F1 | 60%–75% | 85%–92% | 83%–91% | 条款→R1–R30 |
| 关键字段 F1 | 55%–70% | 82%–90% | 80%–89% | 期限/工资/试用期等 |
| 证据 span 命中率 | 50%–65% | 80%–90% | 78%–88% | 必须可回溯 |
| 法条引用准确率 | 低（易编造） | 不交给模型 | 不交给模型 | 只用规则/RAG |

### 5.3 真实预期管理

- 1.5B 模型在“条款分类/字段抽取”上可以接近 7B 的 85%–90%，但**不能替代规则判定**；
- 对同义/口语句式，微调后的召回提升明显；
- 对跨条款引用、复杂否定、地方标准，仍然需要规则和人工；
- 量化后会有 1–3 个百分点的性能下降，必须重新评测。

## 7. 技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 灾难性遗忘 | 通用能力下降，纠错变差 | 混入 10%–20% 通用数据；多任务训练；保留基座对照 |
| 过度纠错 | 把正确内容改错 | 数字/日期/金额锁定；差异展示；<1% 门槛 |
| 幻觉/编造法条 | 报告不可信 | 规则/RAG 提供法条；模型只输出枚举 ID；引用校验 |
| 数据泄漏 | 合同隐私风险 | 本地脱敏；训练数据不出内网；不上传第三方 |
| 分布偏移 | 新合同类型效果下降 | 持续收集困难样本；按类型分层评测 |
| 量化退化 | Q4 后准确率下降 | 评测 Q4/Q5/F16；关键任务保留 Q5 |
| 许可风险 | 无法商用 | 优先 Apache 2.0；发布前法务复核 |
| 移动端性能 | 发热/杀后台 | 1.5B 上限；可选开启；超时降级 |
| 标注不一致 | 学生学到噪声 | 标注规范 + 双人复核 + 规则引擎校验 |
| 版本漂移 | 结果不可复现 | 模型/数据/提示词版本化；固定评测集 |

## 8. 分阶段落地建议

### 阶段 0：数据与评测基线（2–4 周）

- 建立 100–300 份合同评测集；
- 定义 OCR 纠错、条款分类、字段抽取的标注规范；
- 用规则引擎生成高置信标签；
- 跑通基座零样本基线。

**产出**：评测集、基线指标、错误分析报告。

### 阶段 1：1.5B LoRA 纠错（1–2 个月）

- 合成 OCR 噪声 + 真实 paired data；
- QLoRA 微调 Qwen2.5-1.5B；
- 数字/日期守卫 + 差异 UI；
- 目标：CER 相对下降 ≥25%，过度纠错 <1.5%。

**Go 条件**：在目标 Windows 机器上端到端 ≤10 秒，规则命中无回归。

### 阶段 2：1.5B 条款辨认（2–3 个月）

- 条款分类 + 字段抽取 + 规则映射多任务微调；
- JSON Schema 约束解码；
- 规则引擎二次复核；
- 目标：条款分类 ≥88%，规则映射 F1 ≥85%，字段 F1 ≥82%。

### 阶段 3：蒸馏与量化（2–3 个月）

- 7B/14B 教师生成困难样本；
- 序列级 KD + rationale 蒸馏；
- Q4_K_M 量化与重新评测；
- 目标：量化后指标下降 ≤3 个百分点。

### 阶段 4：移动端可选包（3–6 个月）

- Android 1.5B Q4 可选下载；
- 低端机默认纯规则；
- 超时/内存/发热降级；
- 评估包体、耗电、杀后台。

## 9. 结论

### 9.1 可行性评级

| 维度 | 评级 | 说明 |
|---|---|---|
| OCR 纠错 | **可行，优先做** | 任务窄、收益可量化、风险可控 |
| 条款分类/字段抽取 | **可行** | 1.5B + LoRA 可达到生产可用水平 |
| 规则映射 | **可行但需规则兜底** | 模型输出枚举 ID，规则复核 |
| 最终法律判断 | **不可行/不应交给模型** | 需要规则、法条、个案事实 |
| 桌面端部署 | **推荐** | 1.5B Q4 资源可控 |
| 移动端部署 | **有条件可行** | 1.5B 可选包，低端机不默认 |
| 数据与标注 | **主要瓶颈** | 需要真实合同与法律标注 |
| 成本 | **可控** | 无 API 费用，主要是人力与算力 |

### 9.2 最终建议

1. **基座选 Qwen2.5-1.5B-Instruct**，先用 LoRA/QLoRA，不要一开始全参训练。
2. **先做 OCR 纠错，再做条款辨认**；纠错收益更容易量化，风险更低。
3. **条款辨认输出枚举和 span，不输出法条**；法条由规则/RAG 提供。
4. **教师模型用 7B/14B + 规则引擎**，不要完全依赖闭源 API。
5. **量化后必须重测**；Q4 指标下降超过 3 个百分点就退回 Q5/F16。
6. **移动端默认关闭模型**；1.5B 作为可选增强包，低端机走纯规则。
7. **建立评测闭环**：没有评测集不要上线；每次模型/数据/提示词变更都要回归。
